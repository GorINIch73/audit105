# PLAN.md — audit105: аудит счёта 105 (МЗ, ОМС)

**Проект:** `audit105` (исполняемый файл `audit105`).
**Стек:** C++17 · CMake 3.20+ · Dear ImGui (docking) · GLFW + OpenGL3 · SQLite3 · ImGuiFileDialog · zlib · Linux
**Где живёт:** самостоятельное приложение в `/home/gor/Strata/audit` — свои `CMakeLists.txt`, `src/`, `data/`, своя база. С `~/Strata/FinAudit` ничего не разделяется: ни кода, ни БД, ни сборки.
**Референс:** `~/Strata/FinAudit` (FnAudit) — **проверенный рабочий проект** с отлаженным и удобным функционалом. Он используется как **образец логики работы и интерфейса**: докинг, формы-вьюхи, фильтры/сортировка, подтверждение групповых операций, прогресс импорта с отменой, статус-бар, экспорт ODS, бэкап и отчёт о целостности. Берутся паттерны взаимодействия, а не код: сложные механизмы FnAudit (ЖО4, сверка, реестровые номера, собственный PDF-движок, «избирательная очистка») в audit105 **не переносятся**.

## 2. Основной сценарий и структура

**Сценарий:** пользователь выгружает ОДС счёта 105 из 1С (XLS/XLSX/ODS/XML) → `ImportView`: выбрать файл, указать медучреждение, период и примечание (три свободных текстовых поля) → импорт как отдельный прогон с датой импорта → `RunsView`: реестр импортов, фильтр по учреждению, году, примечанию, «недавно импортированные» → `MzFormView`: фильтры, цветовая разметка по категориям, разбор позиций, примечания и реквизиты документов → `ReportsView`: сводка и выгрузка отчёта (HTML/CSV). ## 3. Модель данных: один файл базы

**Один SQLite-файл** (`audit105.db`) содержит всё: реестр импортов, данные прогонов и справочники. Файл можно создать заново, открыть другой, сохранить копию.
**Никакого накопления и объединения номенклатуры.** Каждый файл из 1С импортируется «как есть» и живёт отдельно: позиции одного прогона никогда не смешиваются с позициями другого. Прогоны разделяются через `run_id` и реестр `runs` — физически одна таблица, логически независимые наборы данных.

### 3.1 Реестр импортированных оборотов (`runs`)

```sql
PRAGMA journal_mode=WAL; PRAGMA foreign_keys=ON;

CREATE TABLE runs(
  id INTEGER PRIMARY KEY,
  file TEXT NOT NULL, format TEXT,
  organization TEXT,          -- свободный текст
  period TEXT,                -- свободный текст (год, «2026», «1 квартал 2026»)
  note TEXT,                  -- свободный текст
  account TEXT DEFAULT '105', kfo TEXT DEFAULT '7',
  imported_at TEXT NOT NULL,
  items INTEGER, flagged INTEGER, noted INTEGER);
CREATE INDEX idx_runs_imported ON runs(imported_at DESC);
```

**Реестр** — отдельная форма (`RunsView`) со списком прогонов: файл, учреждение, период, примечание, дата импорта, число позиций, число помеченных.
Фильтры реестра: учреждение, период/год, текст примечания, **«недавно импортированные»** (по `imported_at`), сортировка по дате импорта.

Удаление прогона: `DELETE FROM runs WHERE id=?` — каскадно удаляются subaccounts, items, flags, notes. Подтверждение через `ConfirmationModal` с числом удаляемых позиций и суммой.

### 3.2 Данные прогона

```sql
CREATE TABLE subaccounts(
  id INTEGER PRIMARY KEY, run_id INTEGER NOT NULL REFERENCES runs(id) ON DELETE CASCADE,
  code TEXT NOT NULL, is_total INTEGER DEFAULT 0,
  opening REAL, debit REAL, credit REAL, closing REAL);

CREATE TABLE items(
  id INTEGER PRIMARY KEY, run_id INTEGER NOT NULL REFERENCES runs(id) ON DELETE CASCADE,
  subaccount_id INTEGER NOT NULL REFERENCES subaccounts(id) ON DELETE CASCADE,
  row_no INTEGER NOT NULL,
  name_raw TEXT NOT NULL, name_norm TEXT,
  open_debit REAL, open_credit REAL, in_debit REAL, out_credit REAL,
  close_debit REAL, close_credit REAL,
  qty_open REAL, qty_in REAL, qty_out REAL, qty_close REAL,
  unit_price REAL, arith_ok INTEGER DEFAULT 1,
  rule_code TEXT, category TEXT, severity INTEGER DEFAULT 0);

CREATE TABLE flags(
  id INTEGER PRIMARY KEY, item_id INTEGER NOT NULL REFERENCES items(id) ON DELETE CASCADE,
  rule_code TEXT NOT NULL, category TEXT NOT NULL, severity INTEGER DEFAULT 1,
  amount REAL, rationale TEXT);

CREATE TABLE notes(
  id INTEGER PRIMARY KEY, item_id INTEGER NOT NULL REFERENCES items(id) ON DELETE CASCADE,
  note TEXT, doc_no TEXT, doc_date TEXT, contract TEXT, purchase_date TEXT,
  author TEXT, created_at TEXT);
```

Позиция содержит ровно то, что есть в ведомости: **входящий остаток, приход (дебет), расход (кредит), исходящий остаток** — и в деньгах, и в количестве.

### 3.3 Справочники (в той же базе, но не связаны с `runs`)

```sql
CREATE TABLE categories(
  id INTEGER PRIMARY KEY, name TEXT UNIQUE NOT NULL, color TEXT NOT NULL,
  description TEXT, sort_order INTEGER DEFAULT 0, active INTEGER DEFAULT 1);

CREATE TABLE rules(
  id INTEGER PRIMARY KEY, code TEXT UNIQUE,
  category TEXT NOT NULL REFERENCES categories(name),
  type TEXT NOT NULL,               -- exact|synonym|regex|term|structural
  pattern TEXT NOT NULL, severity INTEGER DEFAULT 1,
  rationale TEXT, source_doc TEXT, active INTEGER DEFAULT 1, updated_at TEXT);

CREATE TABLE terms(
  id INTEGER PRIMARY KEY, rule_code TEXT REFERENCES rules(code),
  term TEXT NOT NULL, term_norm TEXT NOT NULL,
  scope TEXT DEFAULT 'local',              -- local|federal
  origin TEXT DEFAULT 'manual',            -- manual|import (import не трогает manual)
  list_name TEXT, source_doc TEXT, as_of_date TEXT,
  active INTEGER DEFAULT 1, created_at TEXT, updated_at TEXT);
CREATE UNIQUE INDEX idx_terms_norm ON terms(term_norm, scope) WHERE active=1;

CREATE TABLE kinds(id INTEGER PRIMARY KEY, kind TEXT UNIQUE, shelf_life_months INTEGER,
  consumable INTEGER DEFAULT 0, note TEXT);

CREATE TABLE sources(id INTEGER PRIMARY KEY, name TEXT NOT NULL, file TEXT,
  as_of_date TEXT, imported_at TEXT, rows INTEGER, active INTEGER DEFAULT 1);

CREATE TABLE conflicts(
  id INTEGER PRIMARY KEY, term_norm TEXT NOT NULL,
  manual_id INTEGER REFERENCES terms(id), import_id INTEGER REFERENCES terms(id),
  resolved INTEGER DEFAULT 0, resolution TEXT, created_at TEXT);
```

`items.rule_code` — текст, а не FK: справочник и данные импорта не связаны, удаление прогона не ломает правила и наоборот.

Схема — apply-if-missing, миграций до 1.0 нет.

### 3.4 Работа с файлом базы
- **Новая база** — создать пустой `.db` и при желании загрузить справочники из пакета.
- **Открыть** — выбрать другой файл базы (в окне виден путь и имя текущей).
- **Сохранить как** — копия текущей базы (SQLite backup API) с указанием имени.
- **Бэкап** — периодическая копия в `~/.audit105/backups/`.

### 3.5 Пакет справочников (перенос настроек)
Экспорт настроек в один файл `refs_bundle.zip`: категории, правила, термины, типы позиций, источники.
Импорт пакета в новую чистую базу:
- категории, правила, типы позиций — переносятся целиком;
- термины: ручные (`origin='manual'`) не перезаписываются, импортные обновляются по ключу `(term_norm, scope)`;
- совпадения попадают в `conflicts` и разрешаются в UI.
Данные прогонов (позиции, примечания) в пакет **не входят** — переносится только настройка анализа.

## 4. Импорт из 1С

Пользователь сам выгружает ОДС счёта 105 из 1С в **XLS / XLSX / ODS / XML**. Приложение читает любой из этих форматов напрямую, сводит к одной внутренней сетке и дальше работает с ней одинаково.

### 4.1 Форматы и стратегия чтения

| Формат | Как читаем | Примечание |
|---|---|---|
| `.ods` | zip + inflate (zlib) → `content.xml`, `<table:table-row>` / `<table:cell>` | основной, проверен на реальных файлах |
| `.xlsx` | zip + inflate → `xl/worksheets/sheet1.xml` + `xl/sharedStrings.xml` | тот же GridModel, merged-ячейки через `<mergeCell>` |
| `.xls` (legacy binary) | бинарный формат не парсим: `soffice --headless --convert-to ods` (или `csv`) и дальше как ODS | LibreOffice есть в системе; если его нет — просим пользователя сохранить в xlsx/ods |
| `.xml` (выгрузка 1С) | plain XML, `<row>`/`<cell>` (значение в атрибуте `value` или в тексте) | детект по корневому элементу; нужен образец выгрузки |

Общий слой:
```
File → FormatDetector (по расширению + сигнатуре magic bytes)
     → Reader (OdsReader | XlsxReader | XlsViaSoffice | XmlReader)
     → Spreadsheet { name, rows: vector<vector<Cell>> }   // Cell: text, numeric, span
     → PositionParser → Item[]
```
Все читатели обязаны выдавать **абсолютные индексы колонок** (с учётом span/repeat/merge) и **текстовые числа как строки** — нормализация чисел (`\xa0`, `,` → `.`) делается один раз в `PositionParser`, а не в каждом читателе.

### 4.2 Проверенные особенности ODS (2025/2026)
- Один лист, 3300–3600 строк, 1639 позиций (2026) / 1770 (2025).
- `content.xml` сжат deflate → читатель должен поддерживать inflate (zlib).
- Позиция = **две строки**: `Сумма`, затем `Кол.`; субсчёт указан только в строке-заголовке.
- Подитоги `105.00`, `105.30`, `105.31`, `105.33`, `105.34`, `105.35`, `105.36` **исключаются** из позиций (иначе оборот завышается ≈ в 1.8 раза).
- Ширина строк непостоянная: шапка 29–30 условных колонок (две строки шапки между собой не согласованы), позиции 25–29.
- `covered-table-cell` может иметь `number-columns-repeated > 1` — без учёта абсолютная колонка считается неверно.
- Числа в строках позиций — **текст** с `\xa0` и `,` как десятичным разделителем; `office:value` есть только в подитогах.
- Смещение `Сумма` → `Кол.` константное: **−2** (9→7, 19→17, 23→21).
- В 4 позициях цена зашита в название (`... 52,60 р`).

### 4.3 Алгоритм (общий для всех форматов)
1. Reader выдаёт `Spreadsheet`: строки ячеек с абсолютным индексом колонки.
2. Абсолютный индекс каждой ячейки = сумма `number-columns-spanned` + `number-columns-repeated` (ODS) / `mergeCell` (XLSX) покрытых ячеек.
3. Строка с меткой `Сумма` открывает позицию, следующая с `Кол.` закрывает; первая непустая ячейка вида `105.\d\d` = подитог.
4. **Слоты.** Номер колонки не надёжен (слияния «съедают» пустые ячейки). Берём упорядоченный список ненулевых значений и перебором знаков `+`/− проверяем `закрывающее = открывающее ± ...`. На реальных файлах 1641 из 1646 строк разрешаются однозначно; 5 — нет (3 подитог, 2 реальные аномалии). Неразрешимые помечаются как структурная аномалия.
5. `unit_price` = медиана пар «сумма/количество» там, где количество ≠ 0.
6. `row_no` сохраняется — для возврата к строке в размеченном файле.

### 4.4 Профиль импорта
`ImportView` до подтверждения показывает: файл, формат, лист, счёт, КФО, обнаруженные субсчёта, число позиций, число строк с неразрешённой арифметикой. Прогресс и отмена — как в референсном импорте.
Каждый импорт — отдельный `run`; повторная загрузка того же файла создаёт новую версию прогона, старая остаётся для сравнения периодов. Дублирования позиций внутри одного прогона не допускается.

## 5. Правила

Правило привязано к **категории из справочника** (`categories`): «недопустимо по ОМС», «неверный субсчёт», «обратить внимание» — плюс любые, которые добавит пользователь. Порядок применения: `structural → exact → synonym → term → regex`. Позиция может получить несколько категорий; цвет строки определяется доминирующей (по `severity`).

### 5.1 Недопустимо по ОМС
Перечни в `terms`: вакцины/анатоксины/иммуноглобулины, сыворотки, АРТ-препараты, ТБ-препараты, наркология, тест-системы на ВИЧ/гепатиты.
**Сейчас:** внесение только вручную через UI (`origin='manual'`, аудитор указывает категорию, источник и дату). Федеральные справочники подключаются позже импортом (`origin='import'`) — см. §11.
В ОДС колонки источника финансирования **нет** — поэтому категория означает гипотезу: «требуется сверка с планом финансирования», а не доказанное нарушение.
Термин хранится с категорией перечня: `иммуноглобулин` закупается и по ОМС, `изониаз` — ТБ, а не ВИЧ.

### 5.2 Неверный субсчёт
- немедицинское (автозапчасти, стройматериалы, ГСМ) на 105.31/105.36;
- медизделия и расходники на 105.31 (там только ЛП);
- кандидаты в ОС на субсчётах МЗ: тип позиции из справочника `kinds` (оборудование, мебель, транспорт, инвентарь), низкая оборачиваемость, срок службы > 12 мес. Числовых порогов нет; тип позиции заполняет аудитор вручную.
Позиции без заполненного типа категорию не получают, а попадают в очередь на классификацию.

### 5.3 Обратить внимание (структурные и арифметические)
- `закрывающее ≠ открывающее + дебет − кредит` (2 реальные аномалии в 2026);
- сумма > 0 при количестве = 0;
- нет строки `Кол.` или несовпадение числа значений в `Сумма`/`Кол.` (7 пар в 2026);
- отрицательные остатки/количества;
- дубликаты: точные (61 в 2026, 74 в 2025) + fuzzy после нормализации;
- выброс цены единицы по тому же названию в другом прогоне (сравнение, а не объединение данных);
- «замороженные» запасы: оборот = 0 при ненулевом остатке — **обязательно с порогом суммы**, иначе правило шумит (1066 позиций на 25,6 млн ₽, ≈28% закрывающего остатка).

## 6. Форма МЗ

**Выбор прогона.** Вверху — список импортированных файлов (прогонов): файл, медучреждение, период, комментарий, число позиций. Данные каждого прогона — отдельная таблица; переключение между ними не смешивает записи.

**Таблица:** номенклатура | субсчёт | входящий остаток | приход | расход | исходящий остаток | кол. | цена/ед. | категория | правило.

**Фильтры:**
- субсчёт;
- категория (`недопустимо по ОМС`, `неверный субсчёт`, `обратить внимание`);
- **оборот:** только с ненулевым дебетом (закупалось в периоде) / только с ненулевым кредитом / без оборота;
- сумма ≥ X;
- «только помеченные», «только без категории»;
- регистронезависимый поиск по названию.
Итоги по фильтру (число позиций, суммы прихода/расхода/остатка) — в статус-баре.

**Разметка:** фон строки = цвет категории; при нескольких категориях — полосатый фон по доминирующей. Клик по строке → панель деталей (сплиттер): сработавшие правила, арифметика, и **примечания аудитора** — номер и дата накладной, номер договора, дата закупки, текст примечания, кто и когда внесил. Статуса проверки нет: маркером служит сама категория.

**Категории — редактируемый справочник** (таблица `categories`: название, цвет, описание). Пользователь может добавлять свои. Базовые:

| Категория | Цвет | Смысл |
|---|---|---|
| Недопустимо по ОМС | красный | закупка не финансируется ОМС |
| Неверный субсчёт | оранжевый | позиция не на том субсчёте |
| Обратить внимание | жёлтый | требует ручной проверки документов |

Легенда — постоянная панель: количество позиций и сумма по каждой категории.

**Размеченный файл (этап 9, не MVP):** копия исходного `.ods` с фоном ячеек (по `row_no`) и колонками «Правило» / «Причина» — собственный `OdsWriter` (zip, stored entries).

## 8. Справочники и правила

- Категории, правила, термины и типы позиций живут в отдельных таблицах той же базы и **не связаны** с импортированными данными: их можно менять, не трогая прогоны, и удалять прогоны, не трогая справочник.

## 11. Принятые решения

- **Импорт «как есть», без накопления.** Номенклатура не агрегируется и не объединяется между импортами: каждый файл — отдельный прогон со своими позициями.
- **Один файл базы** (`audit105.db`): реестр импортов, данные прогонов и справочники в нём; база создаётся, открывается и сохраняется как файл.
- **Данные и справочники разделены таблицами:** `runs/items/flags/notes` против `categories/rules/terms/kinds`. Связи между ними нет: справочник можно менять, не трогая прогоны, и удалять прогоны, не трогая справочник.
- **Реквизиты прогона — три свободных текстовых поля** (медучреждение, период, примечание) + дата импорта. Реестр (`RunsView`) фильтруется по учреждению, году, примечанию и «недавно импортированные».
- **Итог экспертизы — в самой позиции:** категория (цвет в таблице) и примечание с реквизитами документов. Статуса проверки нет. Поиск накладных, договоров и дат закупки аудитор выполняет руками.
- Перечни ОМС-исключаемых: федеральные как база + локальные дополнения; каждая строка — источник и дата актуализации.
- Граница МЗ/ОС: только качественные признаки, числового порога нет.
- Выход MVP: HTML + CSV; размеченный ODS и PDF — позже.
- Колонки источника финансирования в ОДС нет → категория «недопустимо по ОМС» трактуется как гипотеза, требующая сверки с планом финансирования.
- **Категории — редактируемый справочник** (`categories`: название, цвет, описание). Базовые: «недопустимо по ОМС» (красный), «неверный субсчёт» (оранжевый), «обратить внимание» (жёлтый). Статусов проверки нет.
- **Форматы импорта:** ODS, XLSX, XML читаются напрямую; legacy `.xls` конвертируется через `soffice` в ODS/CSV. Все форматы сводятся к одной сетке (`Spreadsheet`) — правила и форма не знают о формате.
- **Справочники: сейчас только ручное внесение через UI.** Федеральные перечни подключаются позже импортом файлов.
- **Разделение ручных и импортированных данных.** У каждого термина есть `origin`: `manual` или `import`.
  - Импорт **никогда** не изменяет и не удаляет строки с `origin='manual'`.
  - Импорт может создавать и обновлять только строки `origin='import'` того же источника (`source_id`), по ключу `(term_norm, scope)`.
  - Если импортный термин совпадает с ручным — создаётся запись в `conflicts`, в UI показывается «конфликт» с выбором: оставить ручное / принять импортное / объединить. Автоматически не разрешается.
  - Ручное редактирование импортного термина переводит его в `origin='manual'` — следующие импорты его не перезаписывают.
  - Примечание позиции (`notes`) привязано к прогону и в справочник не попадает.
- **Тип позиции и срок службы заполняет аудитор вручную** в очереди классификации; эвристики только предлагают вариант, не применяют его сами.
- **Импорт ОДС по 310 (ОС) отложен** — кандидаты в ОС помечаются без подтверждения, сверка вручную.
- **Пакет справочников** (`refs_bundle.zip`) — экспорт категорий, правил, терминов и типов позиций; позволяет создать чистую базу и сразу загрузить в неё настройки для работы. Позиции и примечания в пакет не входят.
- **Путь к базе настраивается:** `audit105 --db <path>`; по умолчанию `~/.audit105/audit105.db`, бэкапы в `~/.audit105/backups/`. Путь виден и меняется в `SettingsView`.

Формат файла справочника (для будущего импорта, `refs/<источник>_<дата>.csv`, UTF-8):

```csv
scope,category,term,source_doc,as_of_date,note
federal,АРТ,тенопревир,"Приказ ... №...",2025-01-15,
local,Наркология,налфубин,"Локальный перечень, протокол №3",2026-02-01,
```

Дедупликация внутри импорта по `(term_norm, scope)`; термины без `source_doc` и `as_of_date` не принимаются.

## 13. Этап 12 — Справочник перечней вместо «видов перечней»

### Зачем
«Вид перечня» (`list_kinds`) — отдельная сущность, которая ни на что не влияет: она только
метит термины, но перечни при этом остаются группировкой строк `terms.list_name`.
Аудитору нужна **форма редактирования перечней** как самостоятельных справочников:
название, правило, описание, источник, дата актуальности, активность, число терминов.
Поэтому справочник видов удаляется, а перечни становятся отдельной таблицей.

### Схема
```sql
CREATE TABLE IF NOT EXISTS term_lists(
  id INTEGER PRIMARY KEY,
  rule_id INTEGER REFERENCES rules(id) ON DELETE CASCADE,
  name TEXT NOT NULL,
  description TEXT,
  source_doc TEXT,
  as_of_date TEXT,
  active INTEGER DEFAULT 1,
  sort_order INTEGER DEFAULT 0,
  created_at TEXT,
  updated_at TEXT,
  UNIQUE(rule_id, name)
);
```
- Термины продолжают ссылаться на перечень через `(rule_id, list_name)` — миграции `terms`
  не требуется, кроме удаления колонки `list_kind_id`.
- Таблица `list_kinds` удаляется.

### Миграция (в `EnsureSchema`, идемпотентно)
1. Создать `term_lists`, если нет.
2. Если `list_kinds` существует:
   - для каждой пары `(rule_id, list_name)` из `terms` вставить строку `term_lists`
     (источник/дата — из первого термина перечня);
   - удалить колонку `terms.list_kind_id` (через пересоздание таблицы, как в существующих миграциях);
   - удалить таблицу `list_kinds`.
3. Убрать индекс `idx_terms_kind`.

### API `Database`
Удалить: `ListKind`, `SeedListKinds`, `ListListKinds`, `AddListKind`, `UpdateListKind`,
`DeleteListKind`, `GetListKind`, `CreateBlankListKind`, `DuplicateListKind`,
`FindListKindByName`, `CountListsOfKind`, `CountTermsOfKind`, `SetListKind`,
поля `listKindId`/`listKind` у `Term`.

Добавить:
- `TermList` → `id, ruleId, ruleCode, name, description, sourceDoc, asOfDate, active, sortOrder, termCount, activeTermCount`.
- `ListTermLists()` — перечни из `term_lists` с количеством терминов (включая пустые).
- `GetTermList(int64_t id, TermList& out)`.
- `AddTermList(TermList&)` / `UpdateTermList(TermList&)` — при смене имени обновляет `terms.list_name`.
- `DeleteTermList(int64_t id)` — удаляет перечень и его термины.
- `CreateBlankList(int64_t ruleId)` — пустой перечень.
- `DuplicateTermList(int64_t id, int& copied)` — копия перечня с терминами.
- `EnsureTermList(int64_t ruleId, const std::string& name)` — авто-создание строки `term_lists`
  при добавлении термина с новым именем.

### UI
- Новая форма `src/views/ListsEditorView.{h,cpp}` («Перечни»), пункт меню «Правила → Перечни»:
  - таблица перечней: название, правило, описание, источник, дата, терминов, активен;
  - фильтры: поиск, правило, только активные;
  - toolbar: добавить, копировать, удалить отмеченные, пред/след;
  - форма: название, правило, описание, источник, дата, активность;
  - блок «добавить термины в перечень»: текст построчно + источник/дата.
- `TermsEditorView`: убрать панель «Виды перечней», фильтр по виду, колонку «Вид»,
  групповое назначение вида; оставить выбор перечня и групповые удаления.
- Пакет справочников (`ExportDictionaryPackage`/`ImportDictionaryPackage`) включает перечни.
- Примеры правил: у каждого `term`-правила есть свой перечень (`kSeedTermLists` —
  название, описание, источник, дата актуальности); `EnsureSchema` дополнительно
  дозаполняет `term_lists` из `terms` (backfill) для баз, созданных до этапа 12.
  В форме правила для `term`-типа показывается перечень правила и кнопка «Перечни».

### Тесты
- `test_db`: создание/переименование/дублирование/удаление перечня, авто-создание при добавлении
  термина, количество терминов, отсутствие `list_kinds` после миграции.
- `test_views`: `ListsEditorView` создаётся и рендерится без ошибок.

### Критерий готовности
Сборка и все тесты проходят; в UI нет «Вид перечня»; перечни редактируются в отдельной форме.

## 14. Этап 13 — Ревизия и оптимизация базы

### Зачем
Схема выросла итеративно: часть полей и таблиц дублирует друг друга или не используется вовсе.
Нужно ревизировать базу на избыточность данных и полей и оптимизировать её, не ломая
существующие базы (миграции идемпотентны, apply-if-missing).

### Что проверить (ревизия)
1. **Мёртвые таблицы и поля.** `kinds` и `sources` создаются в `EnsureSchema`, но нигде
   не читаются/пишутся — либо подключить к UI, либо удалить вместе с миграцией.
2. **Денормализация `items`.** `items.rule_id`, `items.category_id`, `items.severity` —
   производные от `flags` «доминирующая отметка». Оставить как кэш только если он реально
   используется в горячих запросах; иначе — view/расчёт на лету и удаление полей.
3. **Ссылка термина на перечень.** `terms.list_name` (текст) дублирует `term_lists.name`;
   связь `(rule_id, list_name)` хрупкая. Проверить переход на `list_id INTEGER REFERENCES
   term_lists(id)` и убрать текстовую колонку после backfill.
4. **Счётчики в `runs`.** `items`, `flagged`, `noted` — денормализованные счётчики, могут
   расходиться с реальными данными; сверять с `COUNT(*)` или пересчитывать при изменении.
5. **Повторяющиеся нормализации.** `items.name_norm`, `terms.term_norm` — проверить, что
   нормализация выполняется один раз и не пересчитывается в каждом запросе/фильтре.
6. **Индексы.** Пройти `PRAGMA index_list` / `EXPLAIN QUERY PLAN` по основным запросам
   (FormView, CompareView, отчёты): убрать неиспользуемые индексы, добавить недостающие
   (например, по `items(run_id, subaccount_id)`, `notes(item_id)` уже есть — проверить).
7. **FK и каскады.** Убедиться, что все внешние ключи объявлены и `PRAGMA foreign_key_check`
   проходит; `items.rule_id`/`category_id` с `ON DELETE SET NULL` — проверить корректность.

### Оптимизация
- **WAL + `PRAGMA journal_mode=WAL`, `foreign_keys=ON`** — зафиксировать в одном месте,
  а не разбросано по коду.
- **Подготовленные statements** переиспользовать в горячих циклах импорта и правил
  (кэш `sqlite3_stmt*` вместо `prepare` на каждую строку).
- **Один транзакционный блок** на импорт/пересчёт правил вместо множества мелких коммитов.
- **Массовые операции** (bulk delete, backfill перечней) — через `INSERT ... ON CONFLICT`
  и один `BEGIN/COMMIT`.
- **Размер файла:** периодический `VACUUM` после массовых удалений; бэкап через SQLite
  backup API (уже есть) — не делать `VACUUM` на живой базе без подтверждения.
- **Отчёт о целостности** (`IntegrityReport`) расширить: число строк по таблицам,
  «осиротевшие» ссылки, дубликаты перечней/терминов, число неиспользуемых индексов.

### Тесты
- `test_db`: после ревизии — отсутствие мёртвых таблиц/полей, `foreign_key_check` чист,
  счётчики `runs` совпадают с `COUNT(*)`, регрессия по числу помеченных позиций не меняется.
- Сравнение размера базы и времени импорта/применения правил до и после (документируется).

### Критерий готовности
Схема без мёртвых таблиц и дублирующих полей; запросы основных форм идут по индексам
(`EXPLAIN` без полного сканирования горячих таблиц); все тесты проходят; существующие базы
миграцируются без потери данных.

## 15. Этап 26 — Федеральные справочники (ЕСКЛП): фильтры по АТХ и ОКПД2

### Зачем
Правила `OMS01…OMS05` сейчас работают на ручных терминах-примерах (вакцин, зидовудин, изониазид…).
Чтобы правило «недопустимо по ОМС» работало без ручного ввода, нужен импорт федеральной
выгрузки ЕСКЛП и фильтрация по международным кодам: **АТХ** для лекарственных средств (ЛС)

## 16. Этап 27 — Прогресс обработки, журнал событий и «залипание» файлового диалога

### Проблема (из практики)
1. Импорт справочника ЕСКЛП (9–90 МБ, до 589 тыс. строк) занимает минуты. Пользователь не
   видит, что работа идёт: интерфейс выглядит зависшим, непонятно — ждать или закрывать.
2. Если в файле нет совпадений с фильтрами, `RegistryImportView` оставляла `parsed = false`
   и каждый кадр вызывала `LoadFile()` → повторный скан того же файла, «бесконечная» загрузка.
3. `ImGuiFileDialog` — синглтон. После неудачного импорта диалог с ключом `RegistryFile`
   оставался открытым: `OpenDialog("ImportFile")` игнорировался (`showDialog == true`),
   `Display("ImportFile")` ничего не рисовал (ключ не совпадает). Файловое окно не
   появлялось до перезапуска приложения.

### Решение
1. **Журнал событий в `App`** (`src/App.h`, `src/App.cpp`): `LogEvent(text, level)`,
   `Events()`, `ClearEvents()`; уровни `LogInfo/LogWarn/LogError/LogSuccess`; метка времени;
   дедупликация подряд идущих одинаковых событий; лимит истории 300.
   `SetStatus()` теперь автоматически пишет в журнал.
2. **Статус-бар (62 px)**: последнее событие, предыдущее событие, счётчик форм и база,
   кнопка «журнал». Отдельное окно «Журнал событий» (Вид → Журнал событий, прокручиваемое,
   кнопка «Очистить») — «всегда видны последние пару строк, полный список — скроллом».
3. **Прогресс**: `SetProgress(text, fraction)` / `ClearProgress()` / `HasProgress()`.
   `fraction < 0` — недетерминированный прогресс (анимация по времени) с подписью
   «идёт обработка, N с — это не зависание».
4. **Фоновое чтение справочника**: `RegistryImportView::StartScan()` запускает
   `std::thread`, `FinishScan()` забирает результат; в UI — прогресс по строкам,
   кнопка «Отменить чтение», «Повторить чтение файла». Деструктор отменяет и join-ит поток.
5. **Импорт по перечням**: `StartImport()` / `StepImport()` — один перечень за кадр,
   прогресс «перечней N из M», каждое перечни фиксируется событием в журнале.
6. **Диалоги**: `App::OpenFileDialog(key, title, filters, config)` закрывает диалог с другим
   ключом перед открытием; `App::ClaimDialog(key)` отмечает, что ключ принадлежит форме;
   `App::CloseStaleDialogs(extraKeys)` в `main.cpp` каждый кадр закрывает диалог, у которого
   нет owning-формы (ключи `NewDbDlg`, `OpenDbDlg`, `SaveDbAsDlg` исключены).
7. **Idle-режим** (`glfwWaitEventsTimeout`) не включается, пока активен прогресс.

### Файлы
- `src/App.h`, `src/App.cpp` — журнал, прогресс, обёртки диалогов, статус-бар, окно журнала.
- `src/main.cpp` — watchdog диалогов, условие idle.
- `src/views/RegistryImportView.{h,cpp}` — `RegistryScanState`, `StartScan`/`FinishScan`,
  прогресс/отмена, пошаговый импорт.
- `src/views/ImportView.{h,cpp}` — флаг `parseAttempted` (разбор не повторяется каждый кадр),
  кнопка «Повторить чтение файла», guarded диалог.
- `src/views/SettingsView.cpp` — guarded диалог `RefsBundle`.
- `src/domain/RegistryImport.{h,cpp}` — `ScanProgress` (rows/matches/totalRows/cancel) в
  `ScanRegistryFile` и `BuildRegistryProfile`.
- `src/domain/XlsxReader.{h,cpp}` — `StreamXlsxRows(..., int* totalRowsOut)`,
  `DimensionMaxRow()` для оценки полной длины листа.

### Тесты
- `tests/test_views.cpp`: журнал пишет и дедуплицирует события; прогресс устанавливается и
  сбрасывается; открытие второго диалога заменяет устаревший; watchdog закрывает «сирой»
  диалог.
- `tests/test_registry.cpp`: счётчики прогресса соответствуют числу строк и совпадений;
  при `cancel = true` проход останавливается с понятной причиной.

### Критерий готовности
- Во время чтения большого справочника интерфейс отвечает, видны прогресс и «сколько прошло».
- После неудачного импорта повторного скана нет; диалог выбора файла снова открывается
  без перезапуска приложения.
- Все тесты (`test_db`, `test_parser`, `test_rules`, `test_registry`, `test_views`) проходят.
